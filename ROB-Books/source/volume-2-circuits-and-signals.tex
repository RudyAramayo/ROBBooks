\chapter{Trace the energy path}

A circuit needs a complete path. A source raises electrical potential, a load changes electrical energy into light, sound, heat, or motion, and a return path completes the loop.

Three ideas help us describe the circuit:

\begin{itemize}
  \item \textbf{Voltage} is electrical potential difference, measured in volts.
  \item \textbf{Current} is the rate of charge flow, measured in amperes.
  \item \textbf{Resistance} describes how strongly a path opposes current, measured in ohms.
\end{itemize}

Ohm's law, $V = I R$, connects them for a resistor. If an LED branch has 5 V, an LED drop of about 2 V, and a 220 $\Omega$ resistor, the estimated current is

\[
I = \frac{5\,\mathrm{V}-2\,\mathrm{V}}{220\,\Omega} \approx 0.014\,\mathrm{A} = 14\,\mathrm{mA}.
\]

\begin{conceptbox}
A formula is a model. Component tolerances, temperature, supply variation, and the LED's real forward voltage change the result. Measure with a suitable meter and compare the model to the observation.
\end{conceptbox}

\section*{Ground is a reference, not magic dirt}

In a low-voltage robot, \textbf{ground} usually names the common reference node used by circuits and signals. Two devices exchanging a voltage signal often need compatible reference levels. Power grounds, noisy motors, sensitive sensors, shields, and chassis connections require a deliberate grounding plan in a large robot.

\chapter{Digital, analog, and PWM}

An Arduino pin can represent information in several ways.

\begin{itemize}
  \item A \textbf{digital output} chooses between two logic states, often called LOW and HIGH.
  \item An \textbf{analog input} measures a voltage and converts it into a number.
  \item \textbf{PWM}, or pulse-width modulation, switches quickly between states. The duty cycle controls the average effect seen by a lamp or motor controller.
\end{itemize}

PWM is not automatically a lower analog voltage. It is a timed pattern.

\begin{center}

  \node[anchor=west] at (0,-0.65) {25 percent duty cycle: short ON time, long OFF time};
\end{tikzpicture}
\end{center}

ROB's tread code uses \texttt{analogWrite(pin, 255 - abs(command))}. That inversion matters: in this firmware, a larger command magnitude produces a smaller PWM output value. The archived vendor material is restricted, so this public edition does not use it to justify the electrical behavior. Verify the real controller with an authorized current public datasheet and a supervised bench test. Do not assume every motor driver works this way.

\begin{buildbox}[title={LED PWM MISSION}]
With a mentor-approved Arduino and LED circuit, write three fixed brightness levels using \texttt{analogWrite}: 32, 128, and 224. Predict which looks brightest. Then make a slow fade. An LED makes PWM visible without moving a heavy mechanism.
\end{buildbox}

\begin{lstlisting}[language=C++,caption={A safe LED fade pattern for a classroom PWM pin.}]
const int LED_PIN = 9;

void setup() {
  pinMode(LED_PIN, OUTPUT);
}

void loop() {
  for (int level = 0; level <= 255; level += 5) {
    analogWrite(LED_PIN, level);
    delay(25);
  }
  for (int level = 255; level >= 0; level -= 5) {
    analogWrite(LED_PIN, level);
    delay(25);
  }
}
\end{lstlisting}

\chapter{The base controller's connections}

\section*{Why the archive contains three names}

Earlier ROB software divided work among sketches named \textbf{Base}, \textbf{Torso}, and \textbf{Head}. Base handled tread, flipper, actuator, IR, and IMU work. The retired Torso sketch sent fourteen servo targets toward a Maestro for head and arm channels. The retired Head sketch experimented with IMU and PIR sensing. Present-day ROB uses only the Base code, according to the builder. The other two files teach us how the design evolved; they are not instructions to find or connect two more boards.

The two Torso files in \texttt{ROBArduino} have the same SHA-256 hash, so they are byte-for-byte duplicates rather than different firmware versions. A filename can look like a revision even when its contents are identical---another reason engineers use hashes and release records.

The checked-in firmware names these connections. Pin numbers are facts about the file, not a verified public wiring harness. ROBController's historical serial log calls the board an Arduino Mega. The exact Arduino-compatible board model, revision, core, and installed library versions are not recorded here.

The current Base sketch says “\texttt{ROB:FIRMWARE=BASE;}\allowbreak\texttt{PROTOCOL=RHAPI-0.1}” at startup and once per second. Cerebro listens without transmitting, tries only USB callout devices, and keeps the port whose message matches. This is safer than guessing a changing \texttt{/dev/cu.*} name or sending test commands to every attached board. The label identifies a firmware role and protocol; it does not certify the wiring or make a motion test safe.

Once connected, the sketch reports six centimeter readings five times per second. Each line starts with \texttt{ROB:IR=} and then gives the fields FL, FR, L, R, BL, and BR. Cerebro draws six SceneKit beams around its robot model: green means at least 25 cm, red means closer than 25 cm, and orange means the data is missing or stale. This display helps an operator notice an obstacle, but infrared sensors have blind spots and material-dependent errors; ``path clear'' is not permission to move without looking.

A TODO is evidence of intent, not evidence that the feature works.

\chapter{Decode the seven-field message}

The base firmware waits for a tilde character, then reads seven signed, fixed-width text fields separated by commas:

\begin{center}
\begin{tcolorbox}[colback=ROBInk,colframe=ROBAccent,width=0.96\textwidth,arc=0mm]
{\ttfamily\color{white}\large
\textcolor{ROBAccent}{\textasciitilde}+0000,+0100,+0000,+0100,+0000,+0000,+0000}
\end{tcolorbox}
\end{center}

The positions are:

\begin{enumerate}
  \item left tread brake;
  \item left tread signed speed;
  \item right tread brake;
  \item right tread signed speed;
  \item flipper brake;
  \item flipper signed speed;
  \item linear actuator signed speed.
\end{enumerate}

The example above releases the brakes and asks both treads for +100, while the flipper and actuator remain at zero. The entire frame is 42 characters when every field is exactly five characters.

\section*{Differential steering}

Two treads can steer without a steering wheel. If both sides move forward at the same speed, the robot travels roughly straight. If one moves forward while the other moves backward, the robot rotates.

\begin{conceptbox}
The message is a \textbf{protocol}: an agreement about order, spelling, valid ranges, and meaning. Protocols let programs written in different languages cooperate. The Mac code can be Objective-C or Swift while the Arduino code is C++, yet both can understand the same frame.
\end{conceptbox}

\section*{Build a safer parser on paper}

The historical parser teaches useful ideas, but it is not a model for finished safety-critical code. It reads when only one byte is known to be available, does not prove all 42 characters arrived, does not validate comma positions or numeric ranges, and stores five characters without a sixth null terminator before calling \texttt{atoi}. A damaged frame could be misread.

A safer receiving state machine would:

\begin{enumerate}
  \item search for the start marker;
  \item collect exactly one bounded frame;
  \item verify all separators and signs;
  \item convert each field only after validation;
  \item reject values outside the allowed range;
  \item update all outputs atomically, or update none;
  \item command a safe stop after a deadline.
\end{enumerate}

\begin{lstlisting}[language=C++,caption={Pseudocode for an all-or-nothing command decoder.}]
if (completeFrameAvailable()) {
  Frame candidate = readBoundedFrame();
  if (candidate.hasValidShape() &&
      candidate.valuesAreInRange()) {
    lastGoodCommand = candidate;
    lastGoodTime = millis();
  } else {
    reportBadFrame();
  }
}

if (millis() - lastGoodTime > COMMAND_DEADLINE_MS) {
  commandNeutralAndBrake();
}
\end{lstlisting}

\begin{buildbox}[title={FRAME INSPECTOR}]

\end{buildbox}

\chapter{IR distance and the IMU}

The source declares six IR objects, but the active warning routine reads only the front and rear pairs. It compares those four readings with 25 cm and counts repeated low readings before announcing a shutdown warning. The left/right pair appears only in commented telemetry.

That is a simple \textbf{temporal filter}: require evidence across several samples. It can reduce single-sample glitches, but it does not solve every problem. Grass, angled surfaces, sunlight, dark material, shiny material, sensor placement, and reflections from the floor can change optical range data.

\begin{fieldnotebox}
The call that reads the IR sensors is active in the current loop. The assignments that would set the forward and backward shutdown flags are commented out. The code therefore still reads and reports warnings, but does not currently assert those movement-inhibit flags. The builder reports disabling the behavior after many grass-triggered stops. The final policy and calibration need measurement before publication as a safety feature.
\end{fieldnotebox}

\section*{Three sensors become orientation}

The MPU9250 combines three sensor families:

\begin{itemize}
  \item accelerometer: linear acceleration and gravity;
  \item gyroscope: rotation rate;
  \item magnetometer: magnetic field direction.
\end{itemize}

The firmware uses a Mahony quaternion filter, then prints yaw, pitch, and roll. This is \textbf{sensor fusion}: combine imperfect measurements to estimate a state no single sensor supplies reliably.

\begin{buildbox}[title={FILTER A DATA SET}]
Record ten distance readings from a safe classroom sensor aimed at a box. Compute the mean and median. Move the box, record ten more, and graph both groups. Which summary handles one wild reading better? Do not turn the result into an automatic stop rule without testing more surfaces and conditions.
\end{buildbox}

\chapter{Watchdogs and fail-safe states}

ROB's Arduino loop counts down a two-stage heartbeat. When it expires, the firmware calls the same motor-command function with zero tread, zero flipper, and zero actuator values. However, the timeout passes brake fields of zero, which the code interprets as released brakes. The physical result may be coast rather than hold and must be measured.

The implementation counts loop iterations before checking the second counter, so the exact deadline changes when other loop work changes. It also refreshes the deadline for any received byte before validating a complete frame; malformed traffic could therefore keep an earlier command alive. A production version should refresh only after a valid frame, measure elapsed monotonic time directly, define the safe brake state precisely, and test failures under load.

\begin{conceptbox}
A \textbf{watchdog} asks, ``Did the expected event happen before the deadline?'' A \textbf{fail-safe state} is the state chosen when the answer is no. For a small lamp, OFF may be safe. For a heavy robot on a slope, braking, de-energizing, and mechanical holding behavior must be engineered and tested.
\end{conceptbox}

\begin{safetybox}
The yellow emergency-stop hardware visible in the 2025 bench photograph is not enough to prove a complete emergency-stop circuit. A public robot needs an independently verified stop architecture, clear operator reach, reset rules, contactor or controller behavior appropriate to the hazards, and documented tests.
\end{safetybox}

\begin{buildbox}[title={WATCHDOG WITHOUT MOTORS}]
Program an Arduino LED to remain lit only while a serial ``K'' arrives at least once each second. Stop the sender and confirm that the LED goes dark. Add a latched error LED that requires a deliberate reset. This demonstrates the timing idea without motion.
\end{buildbox}

\begin{lstlisting}[language=C++,caption={A classroom heartbeat pattern using an LED.}]
const unsigned long DEADLINE_MS = 1000;
unsigned long lastHeartbeat = 0;
bool heartbeatSeen = false;

void setup() {
  pinMode(LED_BUILTIN, OUTPUT);
  digitalWrite(LED_BUILTIN, LOW);  // boot stale
  Serial.begin(9600);              // classroom sender
}

void loop() {
  if (Serial.available() && Serial.read() == 'K') {
    lastHeartbeat = millis();
    heartbeatSeen = true;
  }
  bool fresh = heartbeatSeen &&
               millis() - lastHeartbeat <= DEADLINE_MS;
  digitalWrite(LED_BUILTIN, fresh ? HIGH : LOW);
}
\end{lstlisting}

\chapter{Read old code like an engineer}

Historical code is a laboratory notebook. It preserves successful ideas, unfinished experiments, and mistakes. Respect it by asking precise questions.

\begin{tabularx}{\textwidth}{>{\robcondensed\bfseries\color{ROBAccent}}p{1.45in} X}
\toprule
OBSERVATION & ENGINEERING QUESTION\\
\midrule
The rotation test repeats the same Boolean condition twice. & Was the second branch intended to describe the opposite turn? Add unit tests before changing behavior.\\
Some method names, direction comments, and printed labels disagree. & Which direction does each physical tread actually move with each pin state? Record a wheels-off-ground test.\\
Values are not clamped before PWM. & What are the allowed command ranges, and what happens to malformed values?\\
The IR inhibit assignments are commented. & What operating conditions caused false triggers, and what independent protections remain?\\
Ramping and speed feedback are TODOs. & What acceleration, deceleration, encoder, and stopping-distance requirements should a new version meet?\\
The actuator accepts special values 3201 and -3201 to clear safe start. & Should reset be a separate typed command instead of overloading speed?\\
\bottomrule
\end{tabularx}

\begin{advancedbox}
Before modernizing the firmware, build a byte-for-byte protocol fixture and a hardware-in-the-loop test stand with the drive load isolated. Characterize the existing behavior first. A refactor that looks cleaner can still reverse a tread or release a brake.
\end{advancedbox}
