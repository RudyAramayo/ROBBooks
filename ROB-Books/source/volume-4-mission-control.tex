\chapter{One goal, many programs}

Imagine an operator nudges a joystick forward. ROB's controllers encode that gesture in different ways: the current iPhone path places raw joystick coordinates in its legacy snapshot, while the Vision Pro controller derives normalized linear and angular intent. A secure network carries the intent to Cerebro on the Mac mini. Cerebro decides whether that controller owns motion authority, translates the values into the historical base frame, and refreshes the Arduino over USB. The Arduino sets pins. Motor electronics drive the treads.

The USB device name can change when a cable moves to another hub. Current Cerebro therefore scans only USB callout ports, resets each candidate, and listens for the existing Base sketch's exact line, \texttt{BEGIN BASE STARTUP SEQUENCE}. It sends no serial command bytes and requires no Arduino firmware flash. The refresh control closes the old Base connection and runs discovery again. The startup label selects the intended firmware role; it is not authentication and does not prove the harness is safe.

\ROBControlStackDiagram

This architecture separates concerns:

\begin{itemize}
  \item \textbf{Interface}: What does the human mean?
  \item \textbf{Transport}: Which authenticated device sent the message, and is it fresh?
  \item \textbf{Coordination}: Who currently controls the robot, and what behavior is allowed?
  \item \textbf{Hardware adapter}: How does a controller command become ROB's legacy seven-field serial frame?
  \item \textbf{Firmware}: Which output pins and controller bytes represent the command?
  \item \textbf{Physical plant}: What motion actually occurs?
\end{itemize}

\begin{conceptbox}
An \textbf{interface} is a promise between components. It should say valid inputs, outputs, timing, errors, and ownership. Internal code can change while the promise stays stable. That is how large systems remain understandable.
\end{conceptbox}

\chapter{The Mac mini as a robot computer}

Cerebro is the macOS controller and operator interface. Its current source contains several distinct responsibilities:

\begin{fieldnotebox}[title={CEREBRO EXISTED BEFORE THE V5 GIT RESET}]
The current public repository begins with a fresh v5 import from August 2025, but five preserved workshop folders recover the earlier story. A pre-Git v1 archive contains ROB-specific Mac serial-control work dated 2017-2018. The first surviving Git history starts on 1 January 2018, then grows through speech, separate Base/Head/Torso links, depth-camera and hand-tracking experiments, controller arbitration, servos, human tracking, network video, Apple-silicon migration, and early LLM work. The v5 commit created a new Git history around an existing application; it did not create Cerebro in one day. \begin{itemize}
  \item windows and controls for a human operator;
  \item the present Base Arduino serial connection, plus legacy Cerebro paths named for retired Torso and Head Arduinos and servo hardware;
  \item authenticated sessions from controllers and a role-limited lidar publisher;
  \item camera capture, RGB-D helper supervision, Vision processing, and video service;
  \item consent-based local face identity, a private Messages bridge, and explicit training-data recording;
  \item local speech recognition and speech synthesis;
  \item bounded autonomy coordination and optional Gemini integration;
  \item arm scripts and reusable keyframe animation data.
\end{itemize}

The project mixes Swift with Objective-C and Objective-C++. That is not automatically bad. Mature systems often cross language generations. A narrow adapter can let new typed code cooperate with a historical interface while migration happens safely.

\section*{Event loops and state}

A graphical Mac app reacts to events: a button click, a network message, a camera frame, a timer, or serial data. Long work cannot freeze the main event loop. Camera processing drops stale frames rather than building an unlimited backlog. A Python DepthAI helper is supervised as a separate process so a camera disconnect or SDK failure does not crash robot control.

\begin{conceptbox}
This is \textbf{fault isolation}. If one optional subsystem fails, the system reports its own unavailable state while unrelated safety and control paths continue. ``Everything in one giant loop'' is simple only until one slow task blocks every other job.
\end{conceptbox}

\section*{Mac message lab: build, inspect, do not transmit}

The real Mac adapter is Objective-C, but a short Python exercise can reveal the same message shape without opening a serial port. Save this on a Mac and run it in Terminal. It only prints one neutral classroom frame.

\begin{lstlisting}[language=Python,caption={A print-only Mac exercise; it does not connect to ROB.}]
def field(value):
    if not -9999 <= value <= 9999:
        raise ValueError("outside signed five-character range")
    return f"{value:+05d}"

values = [0, 0, 0, 0, 0, 0, 0]
frame = "~" + ",".join(field(value) for value in values)

assert len(frame) == 42
print(frame)
\end{lstlisting}

The companion file \texttt{tools/mac\_serial\_frame\_lab.py} also parses a frame and labels all seven values. A hardware version would need an approved serial device, exact baud configuration, complete input validation, a physical stop path, and supervised tests; those capabilities are intentionally absent from the lab.

\chapter{Phone, Watch, and Vision Pro}
\ROBSourceNow{ROBController/Consciousness/ConsciousViewController.mm}{This is the starting point for the handheld controller UI. Compare its shared message types with the corresponding decoder in Cerebro and the SwiftUI spatial controller under \texttt{ROBControllerVision}.}

ROB has several ways to express operator intent, but only one component should own motion at a time.

\begin{tabularx}{\textwidth}{>{\robcondensed\bfseries\color{ROBAccent}}p{1.05in} X X}
\toprule

Normalized motion usually means values between -1 and +1. That keeps a user interface independent of physical top speed. The robot later converts the normalized request into its configured limits.

The latest operator to press \textbf{Request Control} becomes the drive owner only after Cerebro stops the previous owner's motion. \textbf{Release Control} stops ROB and returns ownership to Cerebro. Each phone/tablet and Vision Pro needs a different paired credential, and the UI displays Cerebro's authoritative owner rather than guessing from a local button.

Vision Pro arm control is a separate domain. Each AMBER arm needs fresh measured seven-joint feedback, position mode, its own time-limited authority, bounded targets, and a hold result. Two PSVR Sense controllers can jog the matching selected joints together only while both grips are held. This is measured joint jogging, not ``move the arm wherever the controller points,'' and it still requires restrained hardware testing.

One readable differential-drive mix is:

\[
L = \operatorname{clamp}(F + T,-1,1), \qquad
R = \operatorname{clamp}(F - T,-1,1)
\]

where $F$ is forward intent and $T$ is turn intent. A speed cap multiplies both outputs before they reach the robot.

\begin{buildbox}[title={JOYSTICK GRAPH}]
Draw a coordinate square from -1 to +1 on each axis. Choose five $(F,T)$ points. Calculate $L$ and $R$, clamp them, and predict the motion. Then reverse the sign convention and notice why written coordinate definitions matter.
\end{buildbox}

\section*{Freshness is part of the command}

Current controller layers use short timing limits: the Vision control model uses a 250 ms lease, the Watch relay uses roughly a 450 ms watchdog, and Cerebro expires a stale control snapshot at about 600 ms. These values belong to different layers and do not prove the Arduino's loop-count heartbeat duration.

\ROBStopChainDiagram

\begin{fieldnotebox}
Cerebro sends one neutral/braked base frame when controller snapshots expire, then stops refreshing USB so the Arduino's independent heartbeat also expires. The current Arduino timeout command uses zero speeds with brake fields that map to released brakes. The physical coast/hold result must be measured; do not call it ``braked'' at the Arduino layer.
\end{fieldnotebox}

\chapter{Pairing and secure robot messages}
\ROBSourceNow{ROBController/Consciousness/AutoNetClient/AutoNetDataTransferProtocol.swift}{This client-side wire-contract implementation is the file being analyzed for identity, framing, authentication, sequencing, and freshness. Compare it with \texttt{Cerebro/Cerebro/AutoNet/AutoNetShared/AutoNetDataTransferProtocol.swift}.}

ROBControl v2 uses a reliable QUIC stream over UDP with TLS 1.3. Cerebro advertises a local Bonjour service named \texttt{\_robctl.\_udp} and uses the application protocol name \texttt{robctl/2}. Those names help a controller find a candidate robot, but discovery alone does not prove identity.

A simplified pairing story is:

\begin{enumerate}
  \item Cerebro creates a code for one named device and one narrow role.
  \item The device stores the robot ID, its own credential ID and secret, and the exact server certificate fingerprint in Keychain.
  \item On connection, TLS protects the link and the device pins the expected certificate.
  \item Both sides prove knowledge of the pairing secret using a fresh challenge.
  \item Each layer performs the checks that apply to its data: transport framing checks size, role, session, and sequence; timestamped sensor messages add capture-time freshness; controller freshness uses Cerebro's local receipt time; and the legacy application payload still needs its own parsing and validation.
\end{enumerate}

\begin{conceptbox}
\textbf{Authentication} asks who the peer is. \textbf{Authorization} asks what that peer may do. ROB's lidar publisher may send typed sensor data but cannot request motion. A controller may request allowed control messages but cannot become a lidar publisher just by changing a word in its own payload.
\end{conceptbox}

\begin{safetybox}[title={NEVER PRINT REAL PAIRING MATERIAL}]
Book screenshots and Maker Faire displays must not reveal enrollment codes, API keys, Wi-Fi passwords, SSH credentials, private keys, device secrets, precise location data, or private console logs. A server certificate fingerprint is a public identity pin, not a secret; it may still be redacted from screenshots as operational metadata. Give every device a unique secret so one device can be revoked without disabling another.

The current iPhone controller requests Always location access and includes live latitude and longitude in each active legacy snapshot. Motion control does not inherently need precise location. Treat this as current privacy debt: remove it, minimize it, or document a specific need and consent policy before a public demonstration.
\end{safetybox}

\begin{buildbox}[title={LOCKED MAILBOX GAME}]
Give three students cards: Operator, Lidar, and Guest. Write allowed message types on role cards. For each pretend packet, check identity first, then role, then sequence number, then freshness. A correctly signed Lidar packet still may not contain a drive command.
\end{buildbox}

\chapter{Control and camera data take separate roads}

Live video is much larger than a joystick command. If both share one congested queue, a delayed camera frame could sit in front of a stop message. Cerebro therefore advertises a separate authenticated \texttt{\_robvideo.\_udp} service using \texttt{robvideo/1}. Independent \texttt{front}, \texttt{belly}, and \texttt{insta360} H.264 feeds each have their own bounded pipeline on the media connection.

The video connection still depends on the exact live control session and the same authenticated controller. The client opens the media stream after authentication and subscribes to each camera separately. If control disconnects, the associated video sessions close. If one video feed fails, control and the other feeds can remain available. On Vision Pro the panorama can appear in a flat window or on an inward-facing mixed-immersive sphere; entering that view brakes motion even when video is intentionally preserved.

\begin{conceptbox}
This is a \textbf{quality-of-service} decision expressed through architecture. Urgent control is small and bounded. Media may drop old frames when the sender falls behind. The freshest useful image is usually better than a growing pile of late images.
\end{conceptbox}

\chapter{How ROB sees space}
\ROBSourceNow{Cerebro/Cerebro/CameraManager.swift}{This file owns a bounded camera/depth delivery path. Lidar acquisition lives separately under \texttt{M2M1-RPLIDAR-iOS-MacOS-Catalyst-/RPLidar}; the chapter names the source when it changes sensor.}

ROB's camera path can produce aligned color and depth. A color pixel describes brightness and color channels. A depth pixel describes estimated distance, currently carried as an unsigned 16-bit number of millimeters; zero means invalid. Alignment lets software ask, ``What distance belongs to this color pixel?'' The builder identifies an OAK-D Pro Wide in the body/belly and an OAK-D Pro autofocus camera at the head/face, while the Insta360 Pro II supplies 360-degree imagery. Each role has its own device identity, socket, helper state, rate budget, and calibration. Luxonis model options differ in field of view, color focus, shutter type, and power demand, so Cerebro should record the product name and board revision returned by the device rather than infer it from appearance.

One supervised Python DepthAI helper owns each selected OAK-D and sends synchronized data to Cerebro through a private local Unix socket. RGB enters the camera/Vision path. Depth travels beside it in a frame set. If a helper or device fails, Cerebro reports that camera's state and retries with bounded backoff instead of terminating robot control. A separate headless Insta360 service maintains camera control, heartbeat, RTMP/ffmpeg preview, demand-driven decode, and six-sector perception.

\section*{Lidar uses polar samples}

RPLidar reports distances at angles around the robot. A point $(r,\theta)$ can be converted into a flat Cartesian point:

\[
x = r\cos\theta, \qquad y = r\sin\theta.
\]

The companion app publishes all valid points that fit its bounded range/count contract, not the former sub-meter front/back slice. Compact \texttt{RLS1} frames carry a fixed header plus four bytes per point; a 720-point scan is about 2.95 KB. Same-Mac delivery prefers authenticated App Group Unix-domain IPC and automatically falls back to the paired QUIC publisher route.

Occupancy maps are a separate product. The app aligns updates using the pose captured with the scan, can save/load/reset \texttt{.robomap} data, and overlays the result on selectable base maps with adjustable scale and north rotation. Rotation is a human calibration unless a trusted heading source exists. A map, route, or destination is context, not permission to drive; stale required sensing still stops the active autonomy path.

The lidar was a later physical stage, braced with three 3/8-inch threaded rods. The builder reports its Ethernet descending to a USB hub through a USB--Ethernet adapter beside the Arduino's USB connection. That mechanical stage needs a measured sensor-to-base transform, vibration check, cable strain relief, and proof that the rods do not intrude into camera or arm envelopes.

\begin{buildbox}[title={DRAW A TINY LIDAR MAP}]
Plot these polar points on graph paper: $(4,0^\circ)$, $(4,90^\circ)$, $(4,180^\circ)$, and $(4,270^\circ)$. Convert each to $(x,y)$. Add noisy points and decide how many samples you need before calling a region occupied.
\end{buildbox}

\begin{advancedbox}
Coordinate frames must be named: sensor frame, robot frame, map frame, camera frame, and arm frame. A point is not useful for grasping until calibrated transforms connect those frames. The repository does not yet contain the complete camera-to-arm calibration, inverse kinematics, collision checking, or verified grasp executor needed for autonomous pickup.
\end{advancedbox}

\chapter{Helpful intelligence, human authority}

Cerebro can recognize speech locally and speak responses through its existing voice path. An optional, explicitly enabled Gemini integration can receive microphone audio and sampled camera frames. That changes the privacy boundary because data may leave the robot for a cloud service.

\section*{A face label is not a key}

Cerebro's separate face-identity feature is disabled by default. A paired operator and a person standing with ROB can confirm enrollment and collect 24 varied examples. Vision checks face position, landmarks, and quality; a selected AdaFace model converts an aligned 112-by-112 crop into a 512-number embedding. The encrypted local gallery stores opaque profile IDs, model-tagged embeddings, and samples with a device-only key. It can delete a whole profile.

WebFace4M is the recommended default encoder; VGGFace2 is available for careful comparison. Their embeddings must never be mixed, and the current distance/margin settings still need false-accept, false-reject, replay, lighting, pose, and occlusion tests on ROB. Recognition expires quickly and enters the scene only as uncertain context. A face called ``administrator'' can personalize a greeting, but it cannot grant control, approve an AI action, run a command, or reveal a secret.

\section*{Messages without robot tools}

The optional Messages bridge is also disabled by default. It accepts only exact allowlisted senders in one-to-one chats, remembers a high-water mark so old messages are not replayed, fails closed on groups/reactions/stale or unexpected items, and limits accepted traffic. Every chat receives an isolated AI conversation with no motor, Music, arbitrary-file, device, camera, or microphone tools.

One bounded image may be normalized without metadata. Optional transcript memory is encrypted, scoped to the same sender/account, bounded, searchable/exportable, and clearable; sending selected excerpts to Gemini is a separate cloud disclosure. Fixed news publishers and Open-Meteo weather provide limited current information without exposing the Mac's location or caller-supplied URLs.

Exact commands from locally configured administrator handles can ask the Mac to shut down or reboot, but only after exact \texttt{YES} from the same sender/chat within 90 seconds. That deterministic path runs before AI, never inserts message text into a shell, and deserves a critical local warning. Do not print real handles or scripts in this book.

\section*{Record evidence only when a human starts it}

An explicit recording session can synchronize face/belly RGB, lossless aligned depth, stereo, calibration, exact lidar, pose, odometry, tread/authority, traversability labels, and separate camera movies. The session is append-only and recoverable; ordinary preview does not silently start it. Requested, observed, and encoded dimensions stay distinct. Autonomous commands may be logged, but they never create their own labels. Consent, free space, retention, deletion, and dataset review remain human responsibilities.

The language model does not receive a tool for arbitrary raw serial bytes. The current schema names five proposals: \texttt{look\_at}, \texttt{play\_gesture}, \texttt{request\_pick}, \texttt{navigate\_relative}, and \texttt{stop\_motion}. Only \texttt{stop\_motion} has an immediate local executor, and its result is deliberately partial: Cerebro can software-stop the base, but arm hold remains unverified. The other four actions do not yet have deterministic executors. Outside autonomy they may reach a controller approval console, but approval records a human decision and does not actuate hardware; during active autonomy they fail as unavailable.

Controller-authorized destination navigation is a separate deterministic feature, not an executor for a model's \texttt{navigate\_relative} proposal. It uses bounded geocoding/planning, a 50 m pilot limit, and fresh pose/map/lidar/depth/authority gates. The OAK sidewalk model may contribute centerline context, and learned traversability comes only from manually traversed, odometry-confirmed ground. Manual takeover or stale required sensing stops the motion path.

\begin{safetybox}[title={PUBLIC CAMERA AND MICROPHONE NOTICE}]
A Maker Faire demonstration should clearly announce when cameras, microphones, recording, or cloud AI are active; provide a visible activity indicator and rapid disable control; avoid collecting unnecessary location or identity data; and obtain appropriate consent, especially around children. The entire Gemini integration defaults off. Once it is enabled, however, the current configuration defaults microphone-audio and camera-frame streaming on unless each is separately disabled; the robot-action tool remains separately off by default. Verify every switch rather than relying on one ``AI enabled'' label.

Face identity, Messages, transcript memory, and recording each have their own enable, consent, retention, and deletion boundary. Turning on one must not silently turn on another.
\end{safetybox}

The operator approves or denies. The simulator returns a measured result. Discuss why ``the model sounded confident'' is not a validation rule.

\chapter{Tests, logs, and reproducible missions}

ROBControllerVision includes a deterministic simulator and a normalized control model. That is a powerful pattern: the same user interface can exercise a simulated endpoint before a physical adapter is selected.

A useful test names:

\begin{itemize}
  \item initial state;
  \item exact input and timestamp;
  \item expected output or rejection;
  \item deadline;
  \item cleanup behavior;
  \item evidence retained when it fails.
\end{itemize}
