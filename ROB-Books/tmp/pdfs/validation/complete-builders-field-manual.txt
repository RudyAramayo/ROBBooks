    NON-NEGOTIABLE SAFETY BOUNDARY

    ROB combines large batteries, high-current brushless motors, chains, treads, flippers, linear motion, long arms,
    machine-tool fabrication, networking, cameras, and software-controlled movement. Qualified adults must
    own the hazard analysis, power protection, emergency-stop architecture, workholding, guarding, lifting, test
    perimeter, and public operation. Never infer a safe circuit or fabrication dimension from a photograph. Never
    treat an ordinary IR sensor, software timeout, or cloud model as safety-rated protective equipment.


   ONE CURRENT ARDUINO, THREE HISTORICAL SKETCHES

   The ROBArduino archive preserves Base, Torso, and Head sketches from an earlier three-Arduino design. The
   builder reports that present-day ROB uses only the Base sketch. This book therefore treats Base behavior
   as the current low-level firmware reference and labels Torso and Head behavior as retired historical evidence.
   Source files cannot prove which binary is flashed today; record the board identity, firmware hash, build envi-
   ronment, and upload date before operation.


   TWO AMBER B1 ARMS, ONE DOCUMENTED CONTROL CHAIN

   ROB carries two seven-joint AMBER B1 arms. The repository snapshot separates their Ubuntu-side cores as
   L-10 and R-11: network clients use UDP or LCM, each core binds a stable CAN interface, and CAN carries com-
   mands and feedback between that core and its arm actuators. The AmberHomeFolder tree is evidence from one
   Ubuntu machine, not a deployable image; never copy its credentials, logs, virtual environment, or machine-
   specific identifiers. Volume 6 documents the inspected protocol, URDF models, reproducible setup, verifica-
   tion gates, and unresolved configuration differences.


   HOW TO FIND THE FILES

   Every printed path is relative to the shared workspace root, /Users/rob/dev in the inspected edition. Start
   at that root, enter the first directory in the path, and follow each slash. Source code is spread across in-
   dependent repositories—including ROBArduino, Cerebro, ROBController, ROBControllerVision, ORobotics, and
   ROBTrainingGames—rather than one giant ROB project. See Presentation/ROB-Books/OPEN-SOURCE-CODE-MAP.md
   for repository locations, licenses, primary files, and commands for finding renamed files.

Design principles that recur
Across the sources, several durable principles emerge:

• use prototypes to discover packaging and load problems;
• separate high-level intent from low-level actuator values;
• keep independent stop layers close to each source of failure;
• isolate optional cameras, Python helpers, video, speech, and AI from core motion control;
• preserve service access and label wiring;
• make unsupported capability fail honestly;
• collect evidence before calling a proposal implemented.

Physical and information paths
The robot contains two overlapping architectures:

1. The energy architecture moves stored electrical energy through protection, conversion, controllers, conductors,
   and motors.
2. The information architecture moves intent and measurements through interfaces, authentication, state ma-
   chines, protocols, adapters, firmware, and feedback.

The two paths meet at motor controllers and actuators. Keeping their documentation separate prevents a common
error: assuming that a correct data value proves the high-current circuit is safe, or that a correctly wired motor proves
the command path is authorized.



Desired component ownership map

Serial frame
        ~+0000,+0100,+0000,+0100,+0000,+0000,+0000


The 42 ASCII bytes represent left brake, left signed speed, right brake, right signed speed, flipper brake, flipper
signed speed, and actuator signed speed. Brake field 0 maps to HIGH and is described as released; nonzero maps
to LOW and is described as engaged. Tread and flipper speed output is 255 - abs(command), consistent with the
active-low motor control concept. The physical brake electronics are not documented by the five-wire motor outline.



Actuator compact serial
The code sends 0x83 to exit safe start, 0x85 for forward, and 0x86 for reverse. It encodes magnitude in a five-bit low
chunk and remaining high bits. Special input values +3201 and -3201 also clear safe start before becoming +3200
or -3200. Reset should be separated from speed in a future typed protocol.

 Safety and correctness audit
 The historical firmware should be preserved as an artifact, then replaced behind fixtures. Priority defects include:

 1. the five-byte numeric buffer lacks a C-string null terminator before atoi and debug printing;
 2. one available byte triggers 41 further reads without proof of a complete frame;
 3. separator positions, signs, ranges, checksum, and frame completeness are not validated;
 4. an extra read after the seventh field can consume the next frame’s start marker;
 5. any received byte refreshes the deadman before frame validation;
 6. the deadman depends on loop counts rather than elapsed monotonic time;
 7. timeout sends zero speed with brake fields that release brakes;
 8. IR inhibit assignments are disabled and would not update outputs until another command path runs;
 9. one rotation test duplicates the same condition and omits the mirrored turn;
10. command values are not clamped to PWM and actuator ranges;
11. ramp constants, encoder feedback, and voltage monitoring are TODO-only;
12. brake, direction, and PWM update ordering has not been proven jerk-free;
13. the flipper and actuator have no firmware-visible end stops, position feedback, or motion timeout;

 A modern base controller should contain:

 • safe GPIO initialization before optional sensors;
 • bounded ring buffer and explicit framed decoder;
 • version, length, type, sequence, range, and checksum validation;

Base heartbeat ownership

gate, not a fixed count of three missed messages. The layered behavior is stronger than either deadline alone, but
the Arduino’s own elapsed time and physical stop result still require measurement.

Camera capture produces a Core Media CMSampleBuffer containing a pixel buffer and timing. Cerebro retains only

Scale into the encoder's pixel format
ROBCameraH264Encoder creates a VTCompressionSession whose destination buffers use video-range bi-planar 4:2:0

At 20 fps, the target interval is 50 ms. Samples arriving sooner are intentionally skipped before conversion. A
dropped allocation or compression result requests a future recovery key frame. Every completion object can be
claimed once, preventing synchronous drop flags and an asynchronous VideoToolbox callback from delivering the
same logical completion twice.



Configure low-latency H.264
The encoder requests real-time operation, disables frame reordering, prefers constrained baseline profile when
supported, supplies expected frame rate and average bitrate, and limits the key-frame interval to approximately
one second. Disabling reordering means this initial stream does not depend on B-frames; decode timestamps can
remain invalid and presentation order follows the reliable stream.

Each encoded result owns copied bytes rather than a borrowed VideoToolbox buffer. The encoder records a mono-

Understand AVCC, SPS, PPS, and access units
H.264 consists of Network Abstraction Layer (NAL) units. Annex-B streams separate NAL units with start codes such
as 00 00 00 01. This implementation does not transmit Annex-B. AVCC stores a big-endian byte length before each
NAL unit. The receiver must use the negotiated length-field width; it must not search for start-code patterns inside
compressed data.
The Sequence Parameter Set (SPS) describes coded properties needed to construct a decoder format. The Picture
Parameter Set (PPS) supplies picture-level decoding parameters. Cerebro sends them in a codec-configuration mes-
sage with a positive generation before access units using that generation. A new configuration, encoder recovery,
or requested key frame resends the configuration. An IDR key frame lets the decoder restart without depending on
earlier reference pictures.

   ADVANCED CHANNEL

   Codec configuration is state, not decoration. A payload can be valid H.264 bytes yet undecodable with the
   wrong SPS/PPS, NAL-length width, dimensions, stream ID, or generation. Validate all of them before asking
   Core Media to allocate decoder state.



Wrap media in two bounded layers
The outer ordered-stream frame is RVID version 1. Its 32-byte header carries magic, version, header length, mes-
sage kind, bounded payload length, monotonic connection sequence, and reserved-zero fields. Authentication,
capability, subscription, feedback, configuration, access-unit, and end messages receive distinct kinds.
Encoded configuration and access units use an inner RBVD version-1 header of 92 bytes. It binds media to ses-
sion UUID, subscription UUID, media sequence, capture time, presentation time, duration, timescale, codec-
configuration generation, NAL-length width, flags, and payload length. Integers are network byte order. Current
hard payload limits are 64 KiB for codec configuration and 2 MiB for one access unit; control JSON is capped at 64
KiB and rejects unknown fields.

Apply backpressure before latency accumulates
Video has its own listener, connections, queue, encoder, authentication domain, and send state. It never shares
the control message queue. Cerebro permits only one pending raw source frame, one pending encoder output

per subscription, and one media send in flight. If encoding or send work is occupied, newer unencoded work is
dropped rather than queued. One actual encoded drop or undeliverable output forces a later IDR; replacing a
not-yet-encoded raw frame does not break decoder references.
Every RVID send has a ten-second completion deadline. A newly accepted stream has 15 seconds to produce its

Decode framing before decoding H.264
On Vision Pro, the Network.framework adapter first reconstructs complete RVID frames from arbitrary receive chunks.
It rejects invalid magic, version, reserved bytes, payload sizes, and ordering before decoding JSON or RBVD. The
media decoder then checks session ID, subscription ID, codec, configuration generation, sequence, timing, AVCC
length width, and size. These checks occur before creating Core Media state.
H264SampleBufferFactory sorts and extracts SPS/PPS, copies their bytes into temporary stable pointers, and calls
CMVideoFormatDescriptionCreateFromH264ParameterSets. It verifies that coded dimensions remain within mac-
roblock rounding of the negotiated size and that clean-aperture presentation dimensions match. This prevents
hostile or corrupted parameter sets from expanding the decoder beyond the agreed geometry.
For each accepted access unit, the factory allocates a CMBlockBuffer, copies the bounded AVCC payload, creates
timing, and asks Core Media to create a ready sample buffer. The not-sync attachment mirrors the key-frame flag.
The display-immediately attachment requests low-latency presentation rather than building a long presentation
queue.



Present and recover without blocking control
The actor-owned H264VideoReceiver feeds an AVSampleBufferVideoRenderer obtained from the UI’s display layer. If
the renderer is temporarily full, it waits only about 50 ms in short cancellable intervals. Continued pressure drops
the access unit and begins recovery rather than accumulating frames.
Sequence gaps, missing configuration, generation mismatch, decoder failure, or requiresFlushToResumeDecoding
make the validator require a key frame. Recovery flushes decoder presentation state, rate-limits key-frame feedback
to no faster than 500 ms, and discards dependent frames until a valid key frame arrives. A configuration-generation
change also flushes before accepting the new decoder state. Statistics report received, rendered, dropped, bytes,
last sequence, and key-frame requests at a bounded update rate.



Timing, reliability, and tradeoffs
Capture wall-clock time measures end-to-end age. Presentation timestamps provide an internal monotonic media
timeline. Duration is derived from the negotiated frame rate. These clocks answer different questions and should
not be substituted for one another.
Ordered reliable QUIC simplifies configuration and access-unit ordering, but packet loss can delay later video
bytes through head-of-line blocking. Because control uses another QUIC connection, video loss does not queue
a stop command, although both flows share Wi-Fi airtime. Future QUIC datagrams would trade retransmission for
application-managed loss recovery and require a new negotiated contract; they are not silently enabled by the
current enum.

Roles
Assign at least these responsibilities:

• Lead operator: owns arm/disarm and the primary controller.
• Safety spotter: watches the robot and crowd, keeps a hand near the physical E-stop, and may stop without

• Educator: explains ROB without distracting the operator.
• Technical support: monitors power, temperature, logs, and recovery.
• Event liaison: coordinates space, charging, barriers, accessibility, and emergency requirements.

One person may fill multiple roles only if workload and risk allow it. Never make the operator answer a long technical

Teach the architecture without
hiding the hazards
The youth sequence and public website should use the same conceptual spine as the engineering record: system
boundary; energy versus information; sense–estimate–plan–validate–act–measure; mechanics and operating enve-
lope; message grammar and freshness; identity and authority; progressive evidence. The explanation may become
simpler, but it must not become false.



A spiral curriculum for ROB
Return to the same ideas with increasing precision. Ages 8–12 classify inputs, outputs, energy, structure, and feed-
back using paper models. Ages 10–14 graph signals, parse bounded messages, and implement current-limited
LED watchdogs. Ages 10–15 model forces, ratios, tolerances, and test ladders. Ages 12–16 reason about state ma-
chines, networking, trust, leases, perception limits, and bounded autonomy. Adult mentors connect each model to
dated evidence and unresolved hazards.

Facilitation pattern
Begin with a phenomenon, not a vocabulary list. Ask learners to notice; collect competing models without ridicule;
choose a measurable prediction; test at the lowest safe energy; compare result and prediction; then introduce
precise language. End by asking what remains unknown. This preserves curiosity while teaching that uncertainty is
an engineering result.

  SAFETY CHECK

  Do not turn ROB into a youth build activity. The public curriculum must not invite access to traction batteries,
  mains or inverter circuits, drivetrain hardware, chains, machine tools, actuators, live controllers, or unrestricted
  network commands. Demonstrations use immobilized hardware, simulation, paper, or separately reviewed
  low-energy kits.

Commission the control path
as one safety-related system
The transport should be verified from discovery through physical response. The current secure path uses Bonjour
discovery, QUIC/TLS, exact certificate pinning, reciprocal pairing proof, a server-owned device role, framed appli-
cation messages, controller freshness, Cerebro’s base heartbeat ownership, and the Arduino’s independent serial
timeout. Each layer needs its own test because success at one layer cannot establish another.



Connection and enrollment matrix
Record clean enrollment, reconnect after launch-order reversal, local-network permission denial, missing Bonjour
TXT metadata, wrong certificate, wrong secret, revoked device, duplicated credential, wrong role, stale sequence,
Wi-Fi loss, and server restart. Capture both endpoint states and verify that no application callback occurs before
authentication completes.

  2026-08-10 TRANSPORT LESSON

  During live commissioning, iOS discovered the sole _robctl._udp service but did not surface its Bonjour TXT
  record. The controller now permits a connection attempt only for that sole metadata-less candidate; the ex-
  act certificate pin and reciprocal proof still fail closed for another robot. A second issue exposed QUIC anti-
  amplification behavior: Cerebro attempted to send the challenge before the client address had enough vali-
  dation traffic. The protocol now begins with a padded client pairing-hello carrying a registry-checked device
  identifier, then sends the fresh challenge. Treat this as a dated implementation note pending tagged release
  and regression fixtures.




Measure the whole stop chain

motion. A green authenticated-link indicator proves identity and readiness; it does not prove command freshness,
brake behavior, or stopping distance.
